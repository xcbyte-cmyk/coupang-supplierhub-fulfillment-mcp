# 화면 전환·비동기 처리 점검

2026-09-17. 기준 커밋: 54c0df5c835b970640e2427f64d4d697cae8a355.
기존 미커밋 작업 위에 필요한 변경만 추가했다. 별도 프레임워크나 자동 재등록은 추가하지 않았다.

## 구현 기준

1. 문제가 생기는 비동기 경계를 먼저 확인하고, 재현 가능한 지연/응답 순서 테스트를 만든다.
2. 대기는 화면을 읽는 동작에만 적용한다. 클릭·업로드·저장·인쇄를 재시도하지 않는다.
3. 요소가 없으면 제한 시간 동안 기다린다. 여러 개면 모호한 상태로 중단한다.
4. 시간 경과는 완료 증거가 아니다. 화면 표시, 목록 변화, 다운로드 이벤트, 저장/출력 원장을 확인한다.
5. 이미 있는 제출 후 unknown 및 중복 실행 방지, 검토 절차는 유지한다.

## 공통 처리

- `src/browser-readiness.ts`: 표시 후보 대기, 표 로딩 종료, 페이지 행 변경, 실행 중인 브라우저 초기화 공유.
- `PersistentChromeSession`과 쉽먼트 세션은 최초 프로필 초기화를 공유한다. 초기화 실패는 다음 호출에서 복구할 수 있다.
- 기존 세션의 500ms/400ms 고정 대기를 제거하고 각 어댑터에서 자신의 준비 표시를 확인한다.
- 다운로드 대기 Promise는 클릭 실패 후에도 거부 처리가 연결되어 있다. native dialog 리스너는 확인 절차가 끝날 때까지 유지한다.
- UI 작업 시작/종료마다 읽기 버전을 변경한다. 오래된 모니터링 결과와 오류는 버전이 다르면 표시하지 않는다.
- 최근 ID 목록은 마지막 요청 결과만 표시하고, Run 읽기 후 선택이 바뀌면 검토 화면 생성 전에 중단한다.
- Run 배정 전 1~3단계의 완료 표시가 작업 종료 시 0으로 돌아가는 표시 조건도 수정했다.

## 유지한 대기

기간 필터 변경 후 600ms, 최초 발주 조회 준비/결과의 2초, 일부 로젠 라디오/입력·OZ 조작의 짧은 대기는 기존 교정과 화면 반응을 고려해 유지했다.
로딩 종료나 실제 성공 결과 확인을 추가하거나 기존 확인을 유지하므로 해당 시간만으로 성공 처리하지 않는다.
검색 응답이 로딩 표시 없이 2초 이후 시작되는 경우까지 해결되었다고 주장하지 않는다. 향후 그런 재현 증거가 나오면 실제 조회 요청/응답과 연결한 대기로 교체한다.
